# Contributing to rust-sitter-mcp

Thanks for contributing! This project is agent-friendly and human-friendly — the same rules apply to both (see the AI policy below).

## Setup

```sh
git clone https://github.com/sdkks/rust-sitter-mcp.git
cd rust-sitter-mcp
make setup    # gate tools + git hooks + verification + build + install
```

(`make install` installs just the release binary — no tests or gate tools.)

**Always install the Git hooks** (`make install-hooks`, included in `make setup`) **before your first commit.** They enforce the project's quality gates locally: staged secret scanning (gitleaks), formatting, clippy with warnings denied, the full test suite, `cargo-deny` (advisories/licenses), `cargo-machete` (unused dependencies), tooling regressions, and the dependency-log rule. CI runs the core gates (fmt, clippy, tests, deny, machete, tooling fixtures, secret scanning) on Linux (amd64 + arm64) for every PR. Two checks are inherently local — the staged-content secret scan and the dependency-log rule — which is one more reason the hooks matter; a PR whose commits skipped the local gates will fail review.

Do not use `--no-verify` unless a maintainer explicitly asks for it in a specific situation (e.g. a release chore). If a gate fails, fix the cause — the gates are the product's safety story.

## Quality gates (what every commit runs)

| Gate | Command (as the hook runs it) |
|---|---|
| Secret scan (staged) | `gitleaks protect --staged` |
| Formatting | `cargo fmt --all -- --check` |
| Lint | `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings` |
| Tests | `cargo test --workspace --all-features --locked` |
| Advisories / licenses | `cargo deny check` |
| Unused dependencies | `cargo machete` |
| Tooling regressions | disposable hook/gate fixtures |

Missing a gate tool? `make install-tools` installs pinned versions (`cargo-deny`, `cargo-machete`; gitleaks via Homebrew, `go install`, or a release binary).

## Commit format

Conventional commits, enforced by the `commit-msg` hook:

```
type(scope)?: subject up to 72 characters

feat | fix | docs | style | refactor | perf | test | build | ci | chore | revert
```

Generated `Merge`/`Revert` subjects are exempt.

## Dependency policy

Adding or re-pinning a dependency requires prior research (currency, alternatives, license/MSRV/features, pin strategy) and a `docs/dependency-log.md` entry **in the same commit**. The pre-commit hook mechanically rejects dependency changes without a log entry. See [AGENTS.md](AGENTS.md) for the full policy — it applies to humans and AI contributors alike.

## AI contribution policy

AI-assisted contributions are welcome, with three rules:

1. **Disclose.** If any part of a contribution (code, docs, tests, commit messages, PR text) was generated by or meaningfully co-authored with an AI tool or coding agent, say so in the PR (the PR template has a checkbox and a free-text line). One sentence is enough — e.g. "code written by Claude Code under human direction" or "patch drafted with Copilot; reviewed and tested line-by-line."
2. **A human is accountable.** Every PR must have a human author who understands and stands behind the change, can answer questions about it, and holds the merge responsibility. AI tools may not be listed as the sole author or maintainer.
3. **The gates are the bar — for everyone.** AI-generated changes pass exactly the same hooks, CI, and review as human-written ones. "The AI wrote it" is neither an excuse for a failing gate nor a reason to skip review. Reviewers may ask for the reasoning behind any change regardless of origin.

We do not ban AI tooling; we require honesty about it. Misrepresenting AI-generated work as purely human (or vice versa) is grounds for rejecting a contribution.

## Pull requests

Open PRs against `main`. The [PR template](.github/pull_request_template.md) checklist mirrors the gates — fill it in honestly (test counts, not adjectives). PRs that ignore the template rules (missing checklist, undisclosed AI assistance where applicable, unexplained gate skips) may be rejected without further review.

Platform expectations: CI validates Linux amd64 + arm64. macOS is validated by the maintainers' local gated workflow (macOS cloud builds are intentionally excluded — cost); if your change touches platform-sensitive code, note what you validated where.

## Repository layout quickref

- `src/` — server, engine, and per-tool modules
- `docs/tools.md` — the complete, normative tool contracts
- `docs/dependency-log.md` — dependency research log (see policy)
- `tests/` — integration suites incl. the deterministic full-flow fixture repository (`tests/support/fixture_gen.rs`, `tests/fixture_smoke.rs`)
- `.githooks/`, `scripts/`, `Makefile` — the gated workflow
