# Split Rust Code into Modules

Use the rust-sitter-mcp MCP server to split, extract, or reorganize Rust code. Discover `suggest_split` and `move_item` before use; optionally discover `get_split_detail` when navigating explicitly retained historical advice. In Pi, MCP exposure depends on configuration: use `tool_search` when the tools are not already exposed (deferred/codemode tools can be loaded this way); in other harnesses, follow that harness's guidance for loading MCP tools. Invoke the exact names and schemas exposed by the client (prefixes vary). The server is **read-only**: advice has no patch, and applicable move plans return patches you review and apply externally.

**Not for:** semantic renames (requires type knowledge), inline `mod x { ... }` body extraction, cross-crate moves, macro-body refactoring, or same-file reordering. By default the engine is syntactic only — it never claims your code compiles. Opt-in evidence flags (Step 3) add bounded, explicitly-configured resolution without ever claiming compilation or equivalence.

**Set expectations first.** Idiomatic application Rust — functions calling methods, prelude types (`Option`, `String`), `#[derive]`/proc-macro attributes, macro invocations (`println!`, `vec!`, `format!`), consumers inside inline `#[cfg(test)]` modules — is exactly what the evidence tiers were built to handle, but the default syntactic-only call still blocks most of it. The standard recipe for application code: pass `assume_standard_prelude: true` plus an explicit `semantic_configuration` (admitted crate graph, edition, declared features/cfg) on `move_item` — under that configuration, prelude types, built-in derives, variant paths, and prelude constructors discharge with real proofs, written re-export routes repair consumer imports automatically, and idiomatic batches reach `applicable: true` (proven end-to-end on a large application crate). Remaining honest walls: excluded trait/unsafe/cfg/generic members (ordinary inherent methods and consts are selectable), macro expansion beyond the bounded declarative declaration-identity tier below, glob-only consumers (surface as `glob_consumer_unrepaired` — migrate the consumer to explicit imports, then re-plan), and sysroot/external-crate member calls. Without the configuration and flag, expect a **design report** (inventory + grouping), not an applicable patch; `supported_unit` eligibility counts overstate what is actually movable. For an impl-dominated file, select whole written inherent methods or consts with their exact header-only `enclosing_impl.anchor`; see associated-item selection below.

## Workflow checklist

- [ ] 1. Call `suggest_split` on the target file → get inventory + drafts
- [ ] 2. Triage advice completeness, review drafts, edit groups/filenames
- [ ] 3. Construct `move_item` batch with exact item anchors
- [ ] 4. Review the plan (rewrites, decisions, trivia)
- [ ] 5. If `applicable: true`, save and apply the patch externally
- [ ] 6. Run `cargo check` from the affected Cargo project

## Step 1: Get split advice

```json
{
  "repo_path": "/absolute/path/to/project",
  "crate_root": "src/lib.rs",
  "source_path": "src/big_file.rs"
}
```

Retention and compact presentation are optional and independent. Defaults are `retain_snapshot:false` and `response_mode:"full"`; compact mode alone does not retain evidence. To request a compact manifest with historical retrieval when available:

```json
{"repo_path":"/absolute/path/to/project","crate_root":"src/lib.rs","source_path":"src/big_file.rs","paths":["src"],"retain_snapshot":true,"response_mode":"compact","limits":{"response_bytes":2097152,"diagnostic_count":0,"text_bytes":0}}
```

A retained result is usable only when `retention.state:"retained"` and an `analysis_handle` is present. Unavailability is explicit and does not by itself make an otherwise complete analysis incomplete. Compact schema 1 reports `analysis_status`, `manifest_complete`, totals, coverage, omissions, and per-collection retrieval availability; it deliberately has no `inventory[]`. `snapshot_id` identifies the corpus; `scope_input_digest` is separate and also binds normalized scope and effective in-root ignore inputs. These digests identify historical evidence, not current freshness. Retention defaults are one active record, 134,217,728 aggregate accounted bytes (128 MiB), and a fixed non-sliding 900-second lifetime from publication. Preparations and in-flight readers occupy capacity; conservative reservation may refuse before final stored charges would fit. The cap is not allocated upfront or a repository-size, response-byte or process-RSS limit. Expiry does not slide with navigation, there is no silent eviction or disk persistence, restart loses handles, and `release` removes the process-local record only. See `docs/tools.md` for the full contract.

- `repo_path`: absolute path to the repository (must be a Git worktree)
- `crate_root`: a Rust source file that declares the module tree (NOT Cargo.toml). For a library crate use `src/lib.rs`; for a binary use `src/main.rs`. If the file sits in a subdirectory, use the root that actually declares its chain.
- `source_path`: the file to analyze (Git-root-relative)

Workspace member roots work the same way: use `member/src/lib.rs` relative to the Git root and admit every ordinary chain hop; no workspace/Cargo discovery occurs. Bare built-in `allow`/`warn`/`deny`/`forbid`/`doc` metadata uses a shared identity-inert classifier and does not obstruct module identity at crate-root or non-root module-file inner attributes or ordinary module declarations. Plain doc strings and `doc = include_str!(...)` qualify without reading or executing their payloads. `cfg_attr` wrapping only that metadata or exact `feature(doc_cfg)` is harmless even with unknown conditions. `no_std`, `no_core`, `macro_use`, `recursion_limit`, other feature gates and unknown/qualified attribute providers retain anchored chain refusals unless a declared cfg wrapper proves its payload inactive. For `move_item` only, `semantic_configuration` can admit active cfg-gated chain edges under one matching root's listed ON features/cfg, without requiring `resolve_semantic:true`. Unknown atoms, known-OFF edges, path remapping, prelude controls, competing declarations/layouts, unadmitted hops and recovery still refuse with chain evidence. `suggest_split` has no cfg opt-in. This chain admission does not clear independent semantic fact, prelude, selected-item or binding vetoes; inspect the configured root's module-evidence assumptions and downstream decisions.

Use `paths` to keep discovery to the smallest useful scope; include `crate_root`, the source, and any files needed for module-chain or written-binding evidence. Omitting `paths` permits repository-wide discovery (large repos can return enormous decision lists); narrowing away required evidence makes the advice incomplete. For a `new_sibling` destination, admit its **directory literal** — e.g. creating `src/tui/new.rs` means `paths: ["src/lib.rs", "src/tui"]` — never the absent filename (`PATH_NOT_FOUND`, `INVALID_DESTINATION`). Note: cross-module binding decisions are usually a minority; most decisions on a big file are intra-file, so narrowing `paths` often does NOT shrink the response.

**Response budget:** inspect `status` (or compact `analysis_status`), coverage, omissions, and truncation reasons. For a full response, if data is withheld for `response_bytes`, retry with `limits: {"response_bytes": 8388608}` (up to 16 MiB); if `retention.state:"retained"`, supported historical collections can also be retrieved. In a complete full response, a nonzero `counts.omissions.duplicate_declaration_display_spans` records only suppressed duplicate declaration displays; it does not mean analysis is missing or require an automatic retry. For compact mode, inspect `manifest_complete`, `totals` (counts), coverage, omissions and per-collection `detail_availability`; a compact manifest has no legacy `inventory[]`. Analysis completion, manifest completeness, page completeness and retrieval availability are distinct. Distinguish server omissions from a client's truncated preview — inspect the saved full response.

## Step 2: Triage and edit the advice

First identify the response envelope. For full schema-2 advice, inspect `status`, `coverage`, `counts.omissions`, `truncation_reasons`, and `draft_eligibility`. For compact `envelope_kind:"split_manifest"` schema 1, inspect `analysis_status`, `manifest_complete`, `coverage`, `omissions`, `totals` (counts), and each `detail_availability` entry; compact has no `inventory[]` to treat as complete. Retrieve details only when the relevant entry says `retrievable:true` and names `get_split_detail`. Keep analysis completion, manifest completeness, returned-page completeness and retrieval availability separate. Failed or incomplete advice requires recovery or explicit acknowledgment of its limits — do not treat it as a complete partition.

The array-by-array guidance below applies to full schema-2 advice or the corresponding full records retrieved from a retained snapshot. Compact mode instead exposes candidate summaries and draft memberships plus the collections it marks retrievable. When detail is available, retrieve only supported collections (`inventory`, `groups`, `decisions`, `advice_decisions`, `companions`, `boundary_observations`, `test_coupling`, `overlaps`, `chain_diagnostics`). For pages, use the same `analysis_handle` and `snapshot_id` (and matching optional `analysis_id`/`scope_input_digest`); page tokens bind collection, filter, page size, ordering and detail limits, so repeat every option unchanged with `selector.page_token`. Filters are limited to `id`, observed typed `reason`, and `candidate_id`. Check `returned_page_complete`, `collection_exhausted` and `next_page_token` independently of analysis status. Example request:

```json
{"analysis_handle":"opaque-analysis-token","snapshot_id":"sha1:captured-corpus-hash","selector":{"kind":"page","collection":"decisions","page_size":100},"limits":{"response_bytes":2097152,"time_budget_ms":60000}}
```

Use a returned full `units` anchor for inspection only; it is frozen historical content with `historical:true` and `live_freshness:"not_checked"`. Detail performs no filesystem read/fingerprint, current-byte check, reanalysis or freshness validation. Before using any unit or header anchor in a move, obtain and verify current bytes, then let `move_item` independently apply its normal exact-anchor and safety checks. Retrieval never auto-selects companions, submits items, or adds an export tool.

- **Full response only — `inventory[]`:** every top-level unit and direct written impl member with `id`, `kind`, `name`, `span.range` (byte offsets). Unnamed impls have `name: null` — handle them by ID. Associated members stay `context_sensitive`; empty `reasons` admits them to drafts, not move safety. Nonempty exclusions and overlapping enclosing impls remain retained. `counts.eligible_items` includes non-excluded associated members. In compact mode, retrieve the `inventory` collection only when available.
- **Full response only — fitted declaration signals:** when `status:"complete"` and `counts.omissions.duplicate_declaration_display_spans` is nonzero, an `item_size` or `name_prefix` signal may have `evidence:[]` because its exact declaration displays are shared with the complete same-response inventory. For these signal kinds only, resolve every existing `signal.item_ids` entry to `inventory[].span`, preserving the IDs' original order. The server applies this tier only after complete-analysis/inventory checks and exact ordered full-descriptor matches; otherwise the existing fail-closed incomplete path applies. Empty fitted evidence means suppressed display copies, not zero observed evidence. Unique reference/consumer occurrences stay direct; do not generalize this fallback. No retained handle or extra call is needed. Reconstructed spans and IDs are display evidence, never execution anchors. Already-fitting arrays and canonical retained records are unchanged.
- Inspect `partition_outcome` first: completed `no_credible_written_partition` preserves inventory/evidence but has no balanced primary. `incomplete_analysis` cannot establish absence of a core. `ownership_candidates[]` is available independently of complete drafts: inspect core IDs, structural signals, integer ranking, companions and whole-impl/member alternatives. Never add companions automatically or select overlapping alternatives. `observed_exclusive` means completed admitted written observations only, not architectural ownership; stopped/ambiguous contexts remain undetermined. Read separately scoped `boundary_observations.coverage` and linked incoming/outgoing records; written routes are not resolved identity, and glob routes are candidates, not repaired consumers. This does not change the local-only forecasts or assess destination/batch applicability.
- Candidate `id` values are response-local `candidate/N` in ranked order; boundary records' `ownership_candidate_ids` link to them. Each companion has its own unique `companion/N` ID ordered by target path/range/kind, then candidate order for repeated targets, plus its inventory `item_id`. Read `review_obligation` from candidate-to-companion association evidence, independently of observed-consumer `classification`, traversal stops and move eligibility: `selection_completeness` asks you to review a supported type/impl association's whole-impl/member shape, retaining any exclusions; `boundary_dependency` identifies written dependencies that may remain in the parent (including exclusive payloads/helpers/constants), subject to move audits; `association_unproved` lacks supported written evidence for the association, without guessing an obligation. None automatically selects a unit or proves access/repairability. These IDs are deterministic for the same inputs, not persistent identities or execution anchors.
- `drafts[]`: up to two proposals. Weak organization facts never form credible cores; with structural advice, the pre-cutover balanced alternative remains low-confidence. Inspect `groups[].rationale`, `groups[].confidence` (confidence is per group, not per draft), sizes, and warnings.
- Members link to their enclosing inventory impl through `enclosing_impl_id`. Follow inventory/group `overlap_ids` into `overlaps[]`: each containment edge names the impl/member IDs and original ranges, with `draft_groups` locating both groups (zero-based indices) in each draft. Different group indices mean cross-group overlap. Affected descriptors/groups carry `size_interpretation.additivity: "non_additive"`; byte/line sizes remain original descriptor values/sums, not unique bytes or generated module sizes. Exact-once IDs do not mean disjoint ranges. Choose the whole impl or members explicitly, never both; no descriptor is silently pruned. In partial responses, check overlap omissions before assuming links resolve.
- Read `test_observations.coverage`, `routes`, `records` and `limitations` separately from legacy test counts and ownership/boundary evidence. Exact `#[cfg(test)]` out-of-line declarations permit conditional discovery to admitted conventional files, not execution admission. Missing/excluded/competing/remapped routes and unlinked marked files are unresolved evidence; never infer Cargo targets/library aliases or interpret zero records as tests unaffected. CST field/path evidence is independent of wrapping, but receiver chains/unrelated types remain unproved. `macro_token_candidate` reports access-shaped macro-input tokens, excluding comments/literals, not expansion or assertion equivalence. Non-exclusive `facade`, `moved_implementation`, `private_state`, `mixed`, `unresolved` labels and candidate links help inspection only: `possible_companion` never selects or mandates moving a test. Check projection omissions/completion before relying on evidence. The exact same-file inline acknowledgement class remains unchanged; out-of-line/third-file glob consumers still block.
- Each candidate/draft group has an uncapped `consequence_summary`: six named classes plus `unmapped`, with exact collection-qualified decision-ID runs. Counts are distinct records per class and **non-additive**; one decision can appear in several classes. Unknown reasons require inspection, never a zero-risk inference. `advice_decisions[]` (`ad/N`) links companion/boundary/test evidence separately from local `decisions[]` (`d/N`); it does not inflate `expected_to_block` or prove outside-consumer repairability. In a full response, omitted detail may need a larger `diagnostic_count`/`response_bytes` retry. In compact mode, use `candidate_summaries` and `draft_memberships` as provided, and retrieve an available `advice_decisions`, `decisions`, `groups`, or other supported collection via `get_split_detail`; unavailable evidence remains unavailable and cannot be recovered by increasing limits. Never guess a link. Fitted `draft_summaries` keep group consequence summaries where membership is retained. Destination/batch applicability stays `not_assessed` even at zero counts. See `docs/tools.md` for the typed mapping and prospective selection-completeness scope.
- `decisions[]`: items needing attention (cross-references, visibility, ambiguity).

With no drafts, read `draft_eligibility.reasons` and `chain_diagnostics`: `response_bytes` means raise the response budget (above); a `no_admitted_nonconflicting_name…` reason usually means the file is already modularized or has too few movable units — a no-draft result there is a legitimate "nothing to do". A `destination: null` group in a draft is the **retain set** — those items stay; omit them from `moves`.

Ordinary mixed flat-file/`mod.rs` chains can produce drafts; conditional edges still require a design report because advice has no cfg opt-in. Impl-heavy files can propose whole non-excluded methods/consts, with local blocker forecasts; a single impl containing only excluded members remains a legitimate no-draft shape. Enclosing impl bodies are not scanned again when member descriptors cover them, so risks are attributed to members without duplicate body observations.

Drafts are advisory; you choose the final grouping:
- Join `drafts[].groups[].item_ids` to `inventory[].id` (IDs, not names, are keys)
- Move items between groups, change destination names, or retain items
- Retain a unit by omitting it from `moves`. `eligibility: "supported_unit"` proves only its kind, not move safety. Context-sensitive uses/modules/macros are inventoried, not automatically movable.
- Name modules after the actual concept (`parser`, `imports`, `sync`), not `part_2` or `utils`

Read `references/rust-modularization.md` before choosing destination names or deciding what to group.

## Step 3: Construct move anchors

For each item to move, build its anchor from the **exact original bytes** and byte range in the inventory:

```python
from pathlib import Path
by_id = {item["id"]: item for item in advice["inventory"]}
root = advice["root"]  # canonical Git root; if null, the response was truncated — recover the budget first
moves = []
for item_id, destination in chosen_groups:
    item = by_id[item_id]
    r = item["span"]["range"]
    raw = (root / item["path"]).read_bytes()
    text = raw[r["start_byte"]:r["end_byte"]].decode("utf-8")
    movement = {
        "item": {"path": item["path"], "range": r, "expected_text": text},
        "destination": destination
    }
    if "enclosing_impl" in item:
        movement["enclosing_impl"] = item["enclosing_impl"]["anchor"]
    moves.append(movement)
```

Run the extraction as a script — **never transcribe `expected_text` from display output**; truncation and multibyte characters will corrupt it (`STALE_SELECTION`).

If `span.text` is `null` or `text_omitted: true`, you must obtain complete bytes this way — display text may be truncated. If complete units came from `get_split_detail`, `units` returns full frozen item/header anchors, but they remain historical (`historical:true`, `live_freshness:"not_checked"`), not checked-current execution authority. Re-read and verify current item bytes and enclosing-impl header anchors before constructing a move request; `move_item` must then independently run its normal freshness and safety audits.

**Probe before large batches.** Submit 1–2 representative items first. If the probe blocks with any `unsupported_in_engine` route — `member_or_constructor_unproved`, `external_or_missing_binding`, `macro_context_unexamined`, `lexical_context_unproved`, `glob_binding_unproved`, `conditional_or_inherited_context` — on the items' own bodies (method calls, prelude/external types, macro invocations, `#[derive]` attributes) **or their consumers** (call sites inside macros, `tokio::select!`, inline test modules), every similar item will block too: that is the syntactic-only boundary, not a recoverable error. Rethink the selection or produce a design report before spending a large call.

Submit all moves as **one batch** (the server plans them together, all-or-nothing):

**Optional `move_item` evidence flags** (default off):

- `assume_standard_prelude` assumes unshadowed type-position `Option`/`Result`/`Box`/`Vec`/`String`, bare value-position `Some`/`None`, and bare built-in derives. Type proofs also admit exactly `std::option::Option`, `std::result::Result`, `std::boxed::Box`, `std::vec::Vec` and `std::string::String` without semantic configuration. Qualified paths bypass the terminal binding: same-name explicit imports do not veto and need no terminal-name audit. The `std` root must remain unshadowed, including written `mod std` declarations or `extern crate ... as std` aliases in the reference's module/block scope chain; original/final root, context, derive, macro and prelude-control audits still apply. Inspect `standard_prelude`, `standard_prelude_constructor` and `standard_builtin_derive` proofs and separate coverage counts. Constructor identity is **assumed with the type, not macro hygiene proved; derive-generated imports are not modeled**: both the constructor spelling and `Option` must be unshadowed under the same original/final module, batch, lexical, derive and prelude-control audits. Other qualified type paths, qualified constructors, patterns and associated calls do not qualify; no import is synthesized.

- `semantic_configuration` also feeds written conditional audits without requiring semantic resolution: selected-item predicates, ordinary module edges, inline modules, imports, required bindings, lexical context and standard-prelude scope. One unique valid entry must match `crate_root`. Features may use `features` or `{key:"feature",value:"name"}` cfg entries. Written and resolution tiers share positive-only `all`/`any`/`not` evaluation; every operand must be known, even behind a determining operand. Unlisted features/keys/values remain unknown, not OFF. Selected items, bindings and module edges must stay active; retained known-OFF context keeps conservative written shadows. `cfg_attr` recurses through active cfg/metadata payloads and skips provably inactive payloads; unknown/malformed predicates, arbitrary providers, active derive payloads and prelude controls retain independent vetoes. Written-only calls keep `integrity.semantic:"not_performed"`, without RA proofs or `resolution_coverage`. Module assumptions and prelude proof bases disclose the declared atoms; retained conditional decisions preserve anchors and disclose consultation in their consequence (raise `diagnostic_count` for complete prose). This does not clear independent macro, access, collision, API, chain or repair blockers.
- `resolve_semantic` requires explicit `semantic_configuration` (admitted crate graph with editions/features/cfg — no sysroot or external paths). Bounded rust-analyzer resolution can prove eligible inherent methods, fields, constructors, enum-variant paths in value/pattern positions, and access at both source and final overlay — never compilation or equivalence. `classification:"variant_path"` anchors the variant and parent enum identities at both ends; generic/unknown parents and unadmitted variant/field attributes still refuse. This is not a general pattern or binder-versus-constant solver. Written conditional audits may independently discharge under the same declared configuration as described above; neither route clears unknown predicates or independent macro, access, API or repair vetoes. Never infer that declaring every Cargo feature makes a batch applicable.
- The RA derive guard distinguishes **nominal identity** from **generated-item-dependent facts**. Nominal path proofs admit well-formed custom/qualified derives only with **stable written declaration or explicit import routes** at both overlays: active locally written declarations or named use leaves (including aliases/grouped uses), with non-glob module/re-export prefixes. Known-OFF imports are not binding evidence (`inactive_written_binding`). Variant segments resolve inside the named enum. Derive-generated explicit imports can override glob-resolved names without a compile error, so globs or unestablished written routes withhold the path proof even if unexpanded RA identities agree. This is not an inert-expansion claim or a Serialize allowlist. Configured extern-prelude dependency roots, methods/field inference/function resolution keep the conservative non-builtin derive veto; generated impls and trait methods are not proved. Both classes evaluate `cfg`/`cfg_attr` with listed ON atoms plus `all`/`any`/`not`; unlisted atoms/features stay unknown (not OFF), and an undeclared `cfg_attr` condition still vetoes everything it wraps. Malformed derives and arbitrary attribute macros still veto. Module macros retain the veto except for the bounded nominal namespace audit below; generated-item context stays strict.
- **Declarative-macro declaration identity**: the same `resolve_semantic` configuration admits type-position paths from an in-crate written `macro_rules!` definition/invocation pair in admitted files. Budget: one `ident` argument, one arm `($name:ident)`, one expansion step, 4,096 significant definition/output tokens and nesting ≤32. Repetition, recursion/nested calls, other fragments, conditional definitions/invocations/enclosing modules (even cfg ON), external/generated definitions and builtins refuse with anchored disclosure. Proc macros execute arbitrary code and **never qualify or run under any flag**; declarative substitution executes none. RA must map the generated name exactly to the written argument, not a literal/fallback range. Output can contain structs/enums and impls, not imports/modules/other namespace-producing items; generated type attributes allow only existing inert lint/doc metadata and unshadowed bare compiler-built-in derives. Other attributes, including `#[serde(transparent)]` even beside `Serialize`/`Deserialize`, and custom/qualified derives refuse as provider-uncertain; helper registration is never inferred from derive spelling. Written declarative definitions cannot provide attributes/derives. Unknown attributes on the written definition/invocation/owners also refuse. This is identity only: generated impls, methods, fields, constructors and variants stay vetoed and unselectable. Inspect `class:"declarative_macro_identity"`, `classification:"declaration_identity"`, null receiver fields and the bounded written-token `basis`; both declaration objects carry exact `declarative_macro:{invocation,definition}` anchors plus the argument anchor, all origin-normalized and compared across overlays. Unconditional counts remain in `coverage.ra_resolved`. Existing accessible public named facade imports can be carried provisionally for bare signature types, with rationale `pending both-overlay declaration identity`; the semantic need remains until both ends pass, no generated canonical terminal is guessed, and conditional/missing/inaccessible facade evidence still blocks. `kind:"declarative_macro"`/`"declarative_macro_definition"` context records disclose admission or `declarative_*` cap/shape/conditional refusal reasons, under `nominal_identity`; their basis does not claim identity already matched. `declarative_attribute_provider_uncertain` names the attribute in a skipped basis, anchoring generated attributes to the whole written definition and written owner attributes to exact source ranges; the invocation is also skipped. Successful identity basis checks resolved ADT and argument provenance at both overlays, not unmodeled rustc replacements. Helper-bearing frozen signatures remain blocked by default; do not strip attributes or weaken containment to restore old proofs. Over-budget/unsupported expansions retain semantic source/final-fact blockers. Independent API/chain/trivia/repair gates remain. Full boundary and reason vocabulary: `docs/tools.md`, section "Declarative-macro declaration identity".
- `assume_declared_helpers` is a separate caller assertion, default `false`, requiring `resolve_semantic:true` and explicit configuration. Use it only when the caller knows each provider-uncertain written or generated struct/enum attribute belongs to a registered derive helper, not a replacing provider. Registration is **not engine-classified** or inferred from spelling. Well-formed companion custom/qualified derive paths on helper-bearing types are checked syntactically only. Inspect distinct `assumed_declared_identity` proofs and `coverage.assumed_declared_identity` (never counted in `coverage.ra_resolved`), plus `assumed_declared_helpers` context reasons naming the reached helper. Identity is **assumed with the type**, with no procedural expansion, hygiene or compilation claim. Both-overlay invocation/definition/argument anchors and access remain required; nominal written-type facts depending on the assumed macro namespace are also labeled conditional. `resolution_coverage.decisions` includes both real and assumed occurrences. The flag never admits control attributes, unknown attributes on non-type written owners, helper-free generated custom/qualified derives, cfg-gated or over-cap definitions, proc-macro construction or generated impl/member/field/constructor/variant facts. Without it, containment is unchanged.
- Selected top-level item attributes also reach configured `resolve_semantic` context checks: listed features may be supplied in `features` or as `cfg` atoms `{key:"feature",value:"name"}`. Review `context_attribute` proofs anchored on the exact attached attribute at both overlays, not the whole item. Active `cfg` and recursively admitted `cfg_attr` can discharge that need; undeclared features/keys remain unknown with anchored `conditional_context` and `undeclared_cfg_atom` disclosure. Known-OFF selected items or required bindings retain `inactive_written_binding`. This does not clear independent prelude/lexical, macro, inline-module, access, API or repair vetoes; never infer that declaring every Cargo feature makes a batch applicable.
- Review `resolution_coverage.context_evaluations` for original/final anchors, status/value/reason, **`fact_class` and `basis`**. The same derive can be nominally admitted and skipped for a generated-item fact; both records remain visible. Anchored `kind:"binding"` checks disclose `stable_written_identity` or `stable_written_identity_unproved`; the latter retains the semantic source/final-fact blocker. Configured external roots instead disclose `configured_dependency_root_with_conservative_context` under the strict fact class. RA proofs also disclose `basis`. A `context_attribute` classification clears only the attribute veto for its stated fact class, not dependent pattern/body resolution, generated implementations or required access repairs; independent chain/trivia/API blockers still apply.
- `acknowledge_test_consumers` discloses only consumers in the moved file's exact inline `#[cfg(test)]` module (including macro arguments) as nonblocking risks; it does not validate tests. Review proof/coverage and acknowledgment decisions; unrelated blockers still block.

Destination rules:
- `{"kind": "existing", "path": "src/destination.rs"}` — append to an existing admitted file; optional `before_item` anchor from that file
- `{"kind": "new_sibling", "path": "src/new_module.rs", "parent_path": "src/lib.rs"}` — create a new file. The path must be a literal `.rs` sibling of **every** assigned source, in a directory that already exists.
- `parent_path` is the ordinary declaring parent, not automatically the source: for `src/source.rs` → `src/moved.rs` it is normally `src/lib.rs`; non-root `foo.rs` declares children in `foo/`.
- Scope (`paths`) must include root, source, destination/parent, and chain/binding evidence. Admit a new file through its existing directory, never its absent filename.
- Build destinations from the accepted request fields only. Advisory `group.destination` also contains `parent_module` and `existing_declaration`; do not copy it verbatim — the strict schema rejects unknown fields.

### Associated-item selection

Inventory includes whole written inherent methods/consts. Supply `enclosing_impl`
from the descriptor's exact header anchor (ending before `{`), not the whole body.
Existing/new-sibling file destinations synthesize audited verbatim `impl_wrapper`
headers and braces. To merge, use `kind:"existing_impl"`, `path`, and `implementation`
anchoring the whole destination impl; optional `before_item` anchors an unselected
member. Headers must be byte-identical and resolve to the same written type.
Unchanged generic/where headers qualify only with preserved written dependencies;
trait/unsafe/negative/attributed impls, cfg/unexamined or generic members and generated
members remain excluded. Review visibility repairs and field-access blockers.
Visibility defaults merge all proven caller module chains at their deepest common
ancestor, emitting `pub(super)`, `pub(in crate::path)` or `pub(crate)` only as needed.
Already sufficient visibility is preserved, and moved private members retain access
from their original defining region. Supported private/restricted internal choices
are rechecked against the merged requirement; an insufficient narrower choice blocks
with `visibility_scope_unproved`, never a silently accepted broken access.
Inspect each visibility rewrite's `visibility` object: exact `consumers[].anchor`
with `access_reason` and original/final consumer module regions, original/final
`defining_region` fields, preserved access requirements and
`narrowest_covering_region` (module-segment arrays; `[]` means crate root).
The defining fields are `original_defining_region` and `final_defining_region`;
the original is null for a synthesized module declaration. A preservation-only
repair has empty consumers and explicitly says no new observed caller. The computed
minimum stays visible even when `after_text` reflects a broader supported override.
This disclosure does not unlock private fields, constructors, unproved concrete types
or uncertain receivers; their anchored blockers still apply.
Associated batches share context evaluations at plan level; per-proof context arrays
are empty. Keep enclosing impl inventory units in the retain set when moving members.

## Step 4: Review the plan

**Require `plan.applicable: true` AND non-null `edits`, `created_files`, `patch`.** A `status: "complete"` envelope does NOT mean the plan is applicable; blocked plans withhold all three artifacts, and preview rewrites are informational only.

Check:
- Historical detail is evidence navigation only: `get_split_detail` does not read current files, check freshness, reanalyze or submit a move. Detail pages expose `returned_page_complete`, `collection_exhausted` and any `next_page_token`; page completeness is not the same as overall analysis or manifest completeness. A `units` result contains full frozen item/header anchors, but `historical:true` and `live_freshness:"not_checked"` mean they are not checked-current execution anchors. Re-read current bytes and independently submit exact anchors to `move_item`, which performs its own checks; no advice ID or unit reference is a move command.
- `binding_proofs[]` and coverage: review `standard_prelude`, `standard_prelude_constructor`, `standard_builtin_derive`, `ra_resolved`, `declarative_macro_identity`, or caller-assumed `assumed_declared_identity` evidence; `integrity.semantic: "resolution_performed"` means bounded resolution only, never compilation/equivalence. For RA evidence, also inspect `resolution_coverage.context_evaluations[]`: its revision, exact attribute/predicate anchor, status/value/reason, fact class and basis describe only reached checks, not an exhaustive inventory. A nominal custom-derive or declarative identity admission does not admit generated-item-dependent facts. Declarative identity additionally requires both written invocation/definition pairs and the argument anchors to match. If an opt-in discharges nothing, inspect each retained decision's `refusal_basis[]` (`class`, `anchor:{path,range?}`, optional `name`) for the actual prelude/derive/shadow/context witness or failed semantic proof stage. Missing ranges indicate unresolved files or synthesized bindings, not guessed offsets. Disclosure changes no veto or override; expand `diagnostic_count` if decision details were omitted.
- `decisions[]` / `blockers[]`: inspect routes, fields, purposes, and choices. A `test_consumer_acknowledged` decision is visible but nonblocking, not proof tests pass; run relevant tests. `lexical_uncertainty.witness_relation: "statement_macro_before_reference"` marks an at-or-before written-token-tree witness; `"block_macro_may_introduce_items"` marks a later standalone macro in the reference's block or an enclosing block that may introduce hoisted items. Neither is a pattern containing the anchor or a hygiene proof (the former `hoist_possibility` relation is no longer emitted). The existing test-consumer opt-in can acknowledge either risk for a namespace-compatible bare reference with a written super import and no other written binding uncertainty; the witness stays visible. Other lexical uncertainties, known binding conflicts, stale anchors, and structural failures still block.
- `rewrites[]`: review every import/path/visibility repair (`before_text`/`after_text`). A `written_reexport` entry in `evidence` marks consumer-side following of named, unconditioned or declared-active `pub use`/`pub(crate) use` leaves (at most eight hops). Check each original hop anchor, the terminal declaration anchor and the chosen declaration/public path in the repair; aliases preserve the consumer's spelling. This is written syntax, not semantic proof or an API shim. Canonical paths remain preferred when visible from the final destination under written private/`pub`/restricted scope. Otherwise the engine searches accessible written public routes to the same terminal, selecting fewest re-export hops then lexicographic absolute path. A fallback's `rationale` discloses `written_reexport_route_fallback`, rejected canonical path/segment, chosen path, candidate count and hop count; anchors retain original/chosen hops, terminal, rejected module and chosen module edges. No canonical module is widened, and terminal attribute/API vetoes remain. Only when no accessible admitted route exists do inaccessible or unprovable segments withhold the rewrite with `refusal_basis.class:"inaccessible_route:<segment>"` and a module-declaration anchor when available. Do not bypass that refusal with a guessed canonical import or visibility widening; see `references/failure-recovery.md`. Globs, unproved/inactive conditioned leaves, cycles and missing declarations still block; moving the re-exported declaration itself still needs an explicit API decision.
- `glob_consumer_unrepaired` blocks when a bare reference in another admitted file may reach a selected item through a visible glob, including `super::super::*` and chained/grouped/module-alias routes. The first anchor names the consumer's exact reference bytes; later anchors contain candidate glob statements, also retained as `glob_import` refusal witnesses. This routes to `selection_change_required`, not an override or semantic/test acknowledgment. Keep the item in place or revise the selected move; do not exclude the consumer from scope to force applicability. Explicit-import and same-file repair paths are unchanged.
- `post_move_import_review` decisions are nonblocking cleanup advisories: the assembled source file has zero written-name references outside the anchored original import for the named bindings, or contains an unenumerable glob. Strings/comments do not count; other written tokens count conservatively. Imports are retained byte-for-byte, including grouped/renamed imports and names mentioned only in strings/comments; public re-exports are excluded. `resolution:"advisory"` and `action.route:"unsupported_in_engine"` here mean review with the caller's compiler externally, not change selection or submit overrides. Token absence does not prove unused traits, cfg or macro-generated uses. After applying the plan, remove only compiler-confirmed unused bindings (preserve surviving group leaves), then rerun `cargo check`; the plan itself does not promise a warning-free build. Only surviving original imports in move-source files are cleanup targets, not entirely synthesized imports or destination-only files.
- `removal_gap` decisions: pure interior removal-boundary gaps longer than two newlines collapse to one blank line by default in multi-item batches only when retained syntax bounds both sides, with an anchored `removal_gap` rewrite. BOF/EOF gaps default to `keep_in_place`, with explicit collapse/retain choices still available. Single-item serialized plans stay byte-identical to their pre-batch-collapse shape, including decision strings and explicit-collapse audit evidence/rationale; single/double newlines and unrelated gaps stay unchanged. Review exact residual `before_text`, candidate `after_text` and both dispositions. Replay the full `action.target` in `rewrite_overrides` with `action:"retain"` to preserve gap bytes or `action:"replace"` plus the exact `removal_gap.after_text` to collapse; omission/`accept_default` follows the disclosed default. Gaps overlapping another repair, sharing a payload-insertion boundary, or containing retained trivia are excluded; a separate repair starting at the gap's end is safe, but start-boundary edits stay excluded.
- `trivia_decisions[]`: review comment/banner ownership.
- `patch`: review the complete git-apply diff and insertion locations.

## Step 5: Apply the patch

Save the complete decoded `plan.patch` unchanged (outside the source tree), then from the returned Git root:

```bash
git apply --check patch.diff
git apply patch.diff
```

Keep or recheck original base bytes/modes plus `created_files[].must_be_absent` before application. `git apply --check` verifies patch applicability, not that the whole analyzed base is unchanged — if anything shifted, regenerate the plan; never discard user edits. Finally run `cargo check` (and relevant tests) from the affected Cargo project or workspace. Resolve any `post_move_import_review` advisories through compiler-backed external cleanup and rerun the check after those edits.

## Gotchas

- **`crate_root` is NOT `Cargo.toml`** — it's a `.rs` source file. A wrong root (e.g., `main.rs` when the tree hangs off `lib.rs`) surfaces in `chain_diagnostics` and linked decisions; inspect them.
- **Anchors go stale after any source edit** — `STALE_SELECTION` means re-read current bytes and rebuild anchors. Never guess offsets.
- **Items inside inline `mod x { ... }` blocks cannot be extracted** — only direct top-level units and supported whole inherent associated units are movable.
- **The engine serializes calls** — `BUSY` means the analysis slot is occupied. The rejected call started no analysis and was not queued. Wait for the active call to finish or cancellation to settle, then retry serially; no retry deadline or other request's identity is disclosed.
- **Trailing newlines are not part of an item's syntax anchor** — inventory byte ranges exclude them.
- **Some MCP clients stringify object parameters** — if a call fails validation with `must be object` (or you see `"limits": "null"` in the error echo), your client serialized `context`/`limits`/`globs` or an explicit `null` into a JSON string. Omit optional object parameters entirely; server defaults apply. Never pass explicit nulls.
- **A complete draft is not move safety** — membership completeness and eligibility say nothing about cross-references, visibility, or macro context. That analysis happens in `move_item`.
- **Chain refusals may name `macro_generated_module_tree` or `root_attribute_chain_uncertainty`** — these are advice-only causes, not override opportunities. Correct the root/scope where possible or stop at a design report.
- **Macro-generated crate roots** (`crate_root!()` / `OUT_DIR` includes) cannot supply a proved ordinary module chain; treat these selections as advice-only.
- **Creating `tests/*.rs` siblings can add Cargo integration-test crates** — module validity cannot see autotest discovery; review the build graph externally.
- **Macro-invocation-as-item files are unsplittable by written-item selection** — generated items are not written inventory units; use advice, not an applicable-split claim.
